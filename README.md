# agent-jumpstart

Sets a team member up with an agent: the **Installer** puts everything on their laptop from one pasted line, and **Jumpstart** is a skill they run once to set up their workspaces. The spec is [#1](https://github.com/Bozodragon/agent-jumpstart/issues/1).

| Folder | What it's for |
| --- | --- |
| `bootstrap/` | The four PowerShell files people paste the address of, and the script that builds the Portall item they're published from. |
| `installer/` | The Node program the pasted line runs. It reads a profile, asks its questions, installs the tools, prints a checklist and says what to do next. |
| `profiles/` | One JSON file per profile (`york`, `default`): the workspace, connector, extra-tool and skill lists, which are ticked by default, what each connector lets the agent do (its `what`, shown after its name when the person is sent to connect it), anything to say under that list when it's ticked (its `note`: for Asana, to choose the team's workspace at the top of Asana's page rather than the one Asana makes for everyone with the organisation's email address, which York's names as york.ac.uk), the top workspace's folder name and whether it lives in Google Drive, the name Software Center lists Google Drive under (`googleDrive.softwareCenter`, York only: with it, a laptop without Drive is checked for a Software Center that offers it; without it, as under `default`, that check never runs) and what's said when it does (`googleDrive.softwareCenterOffer`, in the organisation's words: York's says York's Software Center can install it), how T3 Code's missing settings are filled in (`t3`: the default model, which must be an id T3 knows exactly, such as `claude-opus-5-5`, its effort, and whether Codex is on), and the setup page's address, its line to paste, who to send a log to (`logGoesTo` and `logEmail`, which both the setup page and the log-sharing line use), and its own wording (`setupPage`: where workspaces are, why T3 Code, privacy). A profile may also list its teams (`teams`), which the Installer's first question offers, followed by Another team. Each has a name and may list connectors, extra tools and skills in the profile's own shape: one named like the profile's own (by id, for an extra tool) ticks it, any other is added after the profile's own, ticked, and skills from one of the profile's sources join that source's single add. York's Systems, Data and Operations and Marketing each tick Asana; `default` lists no teams. Adapting the setup for a new team is an edit here, not to the code. |
| `manifest.json` | The pinned version, download address and SHA-256 of each tool the installer installs (Node, Git, the GitHub CLI, clasp and the skills CLI). Bumping a version is an edit here. T3 Code isn't pinned: its entry names the release feeds the installer follows for each channel, and the build is checked against the SHA-512 T3 publishes in them. |
| `skills/` | Skills the installer installs from this repo, such as `jumpstart`. |
| `page/` | The setup page, one source rendered per profile and published to the address in that profile's `page`. See `page/README.md`. |

`.agents/` and `.claude/` hold the skills used to build this repo, not ones the installer ships.

Only Node.js and the command-line tools are pinned. What the pins don't cover:

- clasp and the skills CLI are npm packages pinned by their own tarball's checksum, but their dependencies aren't: neither ships a lock file (`npm-shrinkwrap.json`), so npm picks their dependencies' versions within the packages' ranges on the day, checked only against the registry's own hashes.
- Skills aren't pinned: each comes from its source's default branch on the day, as the profile names it.
- Claude Code is installed with Anthropic's own install script (`irm https://claude.ai/install.ps1 | iex`, run hidden in Windows PowerShell, with its output captured, under a spinner), which installs Anthropic's current release, so its version isn't pinned here.

The installer's code names no workspace, connector, tool or skill: those come from the profile and the manifest. The one exception is the steps the spec fixes for every run: signing in to GitHub with the GitHub CLI, installing the skills with the skills CLI, installing T3 Code, and checking Claude Code. Their manifest ids (`gh`, `t3`, `claude`, `skills`) and GitHub's host (`github.com`) are named once, in `installer/src/manifest.js`, and every step reaches its entry through `toolEntry`.

## The pasted lines

A team member opens Windows PowerShell from the Start menu and pastes one of these:

| Line | What it's for |
| --- | --- |
| `irm https://jumpstart-install.portall.dev/york.ps1 \| iex` | York team members |
| `irm https://jumpstart-install.portall.dev/install.ps1 \| iex` | Everyone else (the `default` profile) |
| `irm https://jumpstart-install.portall.dev/york-debug.ps1 \| iex` | A supervised York test run: debug on, downloads kept |
| `irm https://jumpstart-install.portall.dev/share-log.ps1 \| iex` | Copies the newest installer log to the clipboard, opens its folder and says who to send it to: the person and email in the profile the installer ran with (it reads `profile` from `settings.json`, then that profile's file in `program\profiles\`), or "the person helping you" when it can't tell |

The first three are the same bootstrap with a different top line naming the profile and whether debug is on. It downloads the Node.js zip pinned in `manifest.json`, checks its SHA-256, unpacks it into `%LOCALAPPDATA%\agent-jumpstart\node` (unless that already holds the pinned version), a folder of the installer's own that is never on PATH, so a Node.js the person already has is never moved or replaced; downloads `installer.zip` (this program, its profiles and its dependencies) from the same Portall item into `%LOCALAPPDATA%\agent-jumpstart\program\`, and runs it. Each download prints one line, saying what it is, its size and a percentage that updates in place; the bootstrap reads these from the progress meter of Windows' own `curl.exe` as it downloads. If `curl.exe` is missing or fails (it doesn't use the proxy Windows is set to), `Invoke-WebRequest` downloads instead, and the line gets its size when it's done. It has to work through `irm | iex` on Windows PowerShell 5.1 under Constrained Language Mode, so it stays plain ASCII with no byte-order mark and avoids `exit`, `Add-Type` and .NET method calls; `npm test` checks this.

All four and `installer.zip` are one public Portall item, so one publish ships them together:

```
npm run publish:portall
```

## The setup page

Each profile has its own page showing only its line to paste: [York](https://jumpstart-york.portall.dev/) and [everyone else](https://jumpstart.portall.dev/). `npm run publish:page` renders and publishes both; see `page/README.md`.

## Running the installer

```
npm install
node installer/src/main.js --profile york
```

It writes `settings.json` and a dated log under `%LOCALAPPDATA%\agent-jumpstart\`. The log holds each program that failed, with its exit code and output. It also holds what Anthropic's Claude Code install script printed when it exited 0 and left no `claude.exe` (`Claude Code: installer said: ...`; after a failure it's there as for any program), and Claude Code's own sign-in lines (`Claude Code: sign-in said: ...`, such as `Login failed: ...`), and never the code the person pastes (see Claude Code's sign-in below). A miss the installer expects isn't a failure: a registry value that isn't there (a variable not set, T3 Code not installed) and T3 Code's `ServerAlreadyRunningError` while it starts print nothing on screen, and the log says what they mean in plain words (`T3 Code: not installed yet`, `T3 Code is still starting, so adding … is tried again in 2 seconds`); only a debug log holds the program's own output for them. Git's installer prints nothing, so it's told to keep its own log (`{log}` in the manifest's arguments, `%LOCALAPPDATA%\agent-jumpstart\git-setup.log`), and if it fails, the end of that log is copied into the installer's. Then Git's portable copy (the manifest's `fallback`, pinned and checked like the rest) is unpacked into the same folder instead, which needs no setup and no admin rights; the checklist row says `as a portable copy, because its installer stopped with code N`. With `--debug` (the debug line passes it) the person sees exactly the same questions and checklist, but the log also holds every program the installer ran with its exit code and full output, the user PATH before and after, and the PATH programs are given each time it changes; and the downloads are kept in `%LOCALAPPDATA%\agent-jumpstart\downloads\` rather than deleted after use.

Every program it runs is started with a PATH rebuilt from the registry at that moment: the machine PATH, then the user PATH, with their `%VARIABLES%` expanded, then whatever of the PowerShell window's own PATH isn't already there. The window's PATH dates from when it opened, so this is how the programs it runs see a Git that Software Centre installed since, and the tools this run installs. T3 Code reads PATH only when it starts, and its silent install starts it, so it's installed last, after every tool's PATH entry and after Claude Code. Claude Code's folder (`%USERPROFILE%\.local\bin`, where Anthropic's installer puts `claude.exe` without putting it on PATH) goes on the user PATH first, whether or not Claude Code is there yet. If `claude.exe` isn't there, Anthropic's install script runs hidden, with its output captured, under a spinner (T3's first-run wizard, which would have offered it, is skipped; the script shows no progress of its own), then Claude Code is checked and, if need be, signed in, all before T3 starts. If the script doesn't leave `claude.exe`, the row reads `Not installed: Claude Code's installer didn't finish` and the run carries on.

Claude Code's sign-in runs whenever Claude Code is there but signed out, on a re-run too. A notice headed `Sign in to Claude Code` says first what happens: "A browser window opens at Claude's sign-in page. Sign in there.", "Then come back here. This window carries on by itself.", "If no window opens, copy the link below into your browser." and "Only if the page shows a code: copy it, paste it here and press Enter." Then `claude auth login` runs in the person's window, by `claude.exe`'s full path. It reads from the window itself, so its `Paste code here if prompted >` prompt gets what the person types, and the window shows it as they type; only what Claude prints passes through the installer, on its way to the window, and is kept for the log. Claude prints its lines without its colours or clickable link that way, but the link in full. What follows the prompt on its line is never logged (bar Claude's own `Login successful.` or `Login failed: ...`), so a pasted code can't reach the log even if Claude ever printed it back. One rejected code ends Claude's sign-in, so after a sign-in that didn't sign in, Claude's own `Login failed: ...` line is shown and the person chooses Try again (the default), a fresh `claude auth login` with a new link and code, or Skip for now, which carries on with the rest of the install. It's offered after every failure, with no limit. After a skip, Claude Code's row reads `<version>, not signed in`, and the ending (below) says how to finish. Once T3 has started, the top workspace is added to its project list with T3's own `t3.cmd project add`. Just after T3 starts, its server hasn't yet said it's running, and the command refuses with `ServerAlreadyRunningError`, so it's tried again every 2 seconds for up to two minutes; the checklist says if T3 was still starting after that.

It doesn't open the setup page: the person has just pasted its line, and the browser would take them away from the PowerShell window. Each page it does open (the connectors page, GitHub's sign-up page, an extra tool's settings page) comes with the note "Once you're done in the browser, come back to the Agent Jumpstart window, where you pasted the line, and press Enter." (as does Google Drive's notice to sign in). The window is titled `Agent Jumpstart` for the whole run: the Installer sets its own process title as it starts, on either machine, and the real machine's in-window runners set it again each time a program they ran returns. The Bootstrap can't set it, because Windows PowerShell refuses to under Constrained Language Mode. The old title isn't put back. The log says `Window: Windows Terminal` or `Window: not Windows Terminal, most likely the old console`, by whether `WT_SESSION` was set when the Installer started. Each slow step that shows nothing of its own (each tool's download and install, T3 Code's, which takes about a minute, Claude Code's, which says it's over 300 MB and can take several minutes and ends `Claude Code installed` or `Claude Code not installed: its installer didn't finish`, the check of the skill sources for changes, the skills CLI's runs, waiting for T3 Code or My Drive, and the checks for T3 Code, for Claude Code and for clasp's sign-in) shows a spinner with the time so far; where the output isn't a terminal, as in the tests, it's a plain line instead. The spinner is one line rewritten in place once a second and never cleared, so it doesn't flicker in the old console.

York's window is Windows Terminal on Windows 11, where Windows PowerShell opens inside it, though some laptops still have the old Windows PowerShell console (conhost). It's made for the old console first, and looks the same in Windows Terminal. It prints only characters the old console's fonts draw: printable ASCII, single-line box drawing (`│ ─ ┌ ┐ └ ┘ ├ ┤`) and `•` `·`. The prompt library (`@clack/prompts`) picks its symbols once, as it loads, by guessing whether the window draws Unicode; `installer/src/ui.js` makes the guess yes everywhere, so its guide lines are always box drawing, and prints its other symbols (diamonds, circles, rounded corners) as plain ones (`*`, `o`, `>`, `+`, `-`). Colour is only on symbols and guide lines, and never magenta or blue: the old console draws dark magenta in its own background blue, so dark colours are printed as their bright forms, and magenta and blue as cyan. Every program stays in the pasted-into window: those that print for the person (Claude Code's sign-in, the GitHub and Apps Script sign-ins) run in it, the rest run hidden with their output captured, and pages open in the browser.

The ending comes after the checklist and the log's path. T3 Code is opened at the end of every run that has it, a re-run included, by starting its program with the PATH as it is then, and without waiting for it (a T3 Code that's already open just comes to the front). The one exception is a first run whose install has just started it: its silent installer starts T3 Code, and once its shim is there it isn't started a second time; if the installer didn't start it, the ending does. A T3 Code that isn't installed isn't opened. Then "What to do next" says, when Claude Code, T3 Code and the top workspace all worked, to open the top workspace in T3 Code, start a new conversation and type `/jumpstart`; and, when any step didn't work, to paste the same line again, which tries again what didn't work and skips what's already done. Every step that didn't work is repeated below it with why, as its row said (`T3 Code: Not installed: the download didn't match T3's checksum`), so it can't have scrolled out of sight during the run. A step didn't work when its row starts `Not installed`, `Not checked`, `Not signed in`, `Not switched off`, `Not created` or `Partly off`, ends `, not signed in`, or says a workspace is `not in T3 Code`; skipped, left as it is, already there and not opened yet all count as having worked. The last line is `All done.` or names the steps that didn't work: `One step didn't work: GitHub.` or `These steps didn't work: T3 Code and Workspaces.`. The log holds the same, as `Ending:` lines. The ending is built from a plain structure (`installer/src/ending.js`): the steps that didn't work and why, extra lines to repeat, an optional closing line of its own (for the step it's about; any other step that didn't work is named on one line after it), and whether T3 Code may be opened, so a step that knows better can give its own ending. Claude Code's sign-in, skipped for now, is one: then T3 Code isn't opened (it can't use Claude Code yet; on a first run its silent installer is told not to start it, and nobody is asked to open it from the Start menu; a Workspaces row that's waiting for T3 Code's first start then reads `not in T3 Code yet: it's added when you paste the line again` rather than asking for it to be opened), there's no "What to do next" and no `All done.`, Claude's `Login failed: ...` line is repeated with the steps that didn't work, and the closing line is "One step didn't work: Claude Code isn't signed in, so T3 Code can't use it yet. If T3 Code is open, close it. Then paste the line again: it signs you in and skips everything that's already done." (a T3 Code open during the install reads PATH only when it starts, so it couldn't find Claude Code until it's reopened). When other steps didn't work too, one last line after it names them: `One more step didn't work: GitHub.` or `These steps didn't work either: Git and Skills.`.

It never quietly replaces or duplicates a setup the person already has: anything already in place is either left alone and used, or the person is asked.

- **Tools** (Node.js, Git, the GitHub CLI, clasp): one already on the machine or user PATH outside the installer's folder for it, or in that folder but not put there by the installer, is left as it is, gets no PATH entry, and is the copy later steps use (the GitHub sign-in runs that `gh`, the Apps Script sign-in that `clasp`). Its row reads `<version> (already installed at <folder>, left as it is)`. The installer knows its own copies by the `.installed-by-agent-jumpstart` file it leaves in a tool's folder after each install; only those are updated. A folder of the installer's that holds something else, and not the tool, is left alone and the tool isn't installed. The skills CLI sits off PATH in its own folder and is only ever run by the installer, with the installer's own Node and the bin script its package names, so it never depends on whichever `node` is first on PATH.
- **T3 Code**: one already installed (Windows records its version, or either channel's program is in its folder) isn't downloaded, updated or switched, and the channel isn't asked; the channel found is recorded. Its row reads `<version> (<channel>, already installed, left as it is)`. Its settings, though, get whatever is missing, on every run. T3 Code is set up rather than walked through by two files in `%USERPROFILE%\.t3\userdata\`, which T3 reads only as it starts (so on a new install they're written just before its installer runs, which starts it): `client-settings.json` marks its first-run wizard done (`onboardingCompletedAt`) and turns on usage and context in the floating island's Thread details card (`threadDetailsItems` set to `{"usage": true, "context": true}`), and `settings.json` sets what the profile's `t3` says (Codex off, and new threads on Claude with the model and effort it names). Only what's missing is added: a key the person already has keeps its value, whatever it is, and a file that has all of them isn't written again. So a `threadDetailsItems` with usage or context turned off stays that way, a Codex they've switched on stays on, and their other providers stay beside it. A file that's missing altogether is created with only these keys; one that isn't valid JSON is left as it is, with a line in the log. The legacy context meter (`contextWindowMeterEnabled`) is never written.
- **The top workspace**: the person is always asked where it is ("Where's your top workspace? Your other workspaces go inside it."), unless a re-run already knows. They can choose a project already in T3 Code that looks like one, make a new one where the profile says (in Google Drive, or a folder they then give), or use another folder of their own by typing its path. A folder that's already there is used as it is, whatever it's called, and only the missing workspaces are made inside it; one that isn't is made, if the folder it goes in is there. Google Drive is optional, and the installer never installs it. Google Drive for desktop is looked for only when a new one is made under a Google Drive profile; with it signed in, the new one goes in My Drive. It's told apart by its traces: its program in Program Files (`Google\Drive File Stream\<version>\GoogleDriveFS.exe`), and the data it keeps for each person once it has been opened (`%LOCALAPPDATA%\Google\DriveFS`, with a folder per signed-in account). If it isn't installed and the profile names Drive's entry in Software Center (York), Software Center is checked for, reading only: the Configuration Manager client's service running (`sc.exe query CcmExec`), the `softwarecenter:` protocol registered (`reg.exe query HKCR\softwarecenter`), then Google Drive among what it offers (PowerShell's `Get-CimInstance` on `CCM_Application` in `root\ccm\ClientSDK`, found by name, giving its Id as one line of JSON). A step that finds nothing is logged in plain words, never as a failure. If Software Center offers Drive, the person is told the profile's `googleDrive.softwareCenterOffer` (York's: "Google Drive isn't on this laptop. With it, your workspaces are backed up and you can reach them from any device. York's Software Center can install it for you, with no admin rights needed.") and offered "Install it from Software Center" (first, and the default) or "Use Documents instead". Installing opens Software Center at Drive's entry (`softwarecenter:SoftwareID=<Id>`), says "Click Install in Software Center, then come back to this window." and "If it asks you to restart, choose a later time." (kept until York-laptop check #37 says whether it's needed), and waits, visibly, for up to 15 minutes until Drive's version folder appears in Program Files; then it asks them to open Google Drive from the Start menu and sign in, and waits up to another 15 minutes for the sign-in before carrying on as for one that's installed but not signed in (below). After 15 minutes without Drive, Documents is offered as when there's no Software Center. Drive is never installed by script, nor with Google's own installer, which needs admin rights. Without Software Center, or when it doesn't offer Drive, the person is told "Google Drive isn't on this laptop. Your workspaces can go in Documents instead. They'll be on this laptop only, so they aren't backed up and you can't reach them from another device. Or install Google Drive for desktop first, then paste the line again." and offered "Use Documents" (the default), which makes the new one in `Documents` in their profile folder, or "I'll install Google Drive first", which ends the run there, cleanly and before anything is changed, saying to paste the line again once it's installed. If it's installed but has never been opened, or isn't signed in, they're asked to open Google Drive from the Start menu and sign in, then to say it's signed in, and it's looked for again each time, until it's signed in or they choose "Use Documents instead". With answers from a file nobody is waited for: unless the file chose Documents, the run stops at once. My Drive can take a few seconds to appear after the sign-in, so it's looked for again for up to two minutes before its folder is asked for. A re-run never moves a top workspace that's already there, wherever it is. See `topWorkspace` below.
- **Skills**: one already in Claude's skills folder is left as it is (`Already there, left as it is`) unless this installer installed it before (`skillsInstalled` in `settings.json`); those are added again, which updates them, but only from a source that has changed. Before adding anything, each source's default branch is looked up with `git ls-remote https://github.com/<owner>/<repo>.git HEAD`, and the commit each source was installed from is kept in `settings.json` (`skillSources`). A source still at that commit, with all its skills still in Claude's skills folder, isn't downloaded again, and its skills' rows read `Up to date`; a source that has changed, was never recorded, or couldn't be looked up is added as on a first run, and a first run adds every source. The skills CLI clones each source with Git, so with no `git.exe` on the machine or user PATH after the tools step it isn't run, and each skill's row reads `Not installed: Git is needed and isn't installed`. A profile's `fullSkills` lists Matt Pocock's full set for writing code, apart from `skills`: `finished` and `beta`, both from `mattpocock/skills`. The person is asked whether to add them (after the extra tools, before memory; the answer is `fullSkills`: `no`, `finished` or `beta`, which adds both lists), and the chosen names are merged into the profile's own entry for that source before the step runs, so it's still added, looked up and recorded once. A full-set skill that doesn't arrive (an unfinished one renamed or removed upstream) reads `Not installed: it didn't arrive`, and its source isn't recorded, so it's added again on every run until the profile's lists are edited.
- **Memory**: someone who has been using Claude's automatic memory is asked before it's switched off, and by default it's left on.
- **Sign-ins**: anyone already signed in (Claude, GitHub, clasp) isn't signed in again or sent to the connectors page again, and Git's settings aren't touched for someone already signed in to GitHub.

Running it again carries on and updates what the installer itself put there. If `settings.json` is there for the same profile, its answers are used; only an answer it lacks, or one that no longer fits (a folder that's gone, a name the profile no longer offers), is asked. Every re-run first asks "Anything to change from last time? Tick what to change, or press Enter to keep it all. Unticking something later doesn't remove it." (after the team question, when a profile with teams has no team saved). It lists Team (under a profile with teams), Workspaces, Connectors, Extra tools, GitHub, Skills and Memory, each only when the settings hold its answer; Memory only when there's a sign of memory use or it was left on last time. Each one ticked is asked again in its usual place, with last time's answer as the default (a pick's, without anything the profile no longer offers; never the profile's own ticks), and logged as `Settings: <key> is to change, so it's asked again`. Unticking removes nothing: workspaces, connectors, extra tools, GitHub's sign-in and skills stay. Skills no longer chosen stay in Claude's skills folder and in `skillsInstalled`, and aren't updated; a skills answer that grows adds the full set's source again even at the commit recorded. Memory switched off by an earlier run isn't switched back on: its row says `Still off: the Installer doesn't switch it back on` and `autoMemory` stays `"off"`. A top workspace that's gone is asked about afresh rather than made again; settings from before the top workspace was recorded are taken as a new one where their Google Drive folder or workspaces folder says. To answer everything afresh, delete `settings.json` first. After the questions, a note headed `Using your answers from last time` lists what the settings file answered: the top workspace (when it's the one recorded), T3 Code's channel, GitHub, the ticked workspaces, connectors and extra tools, the skills choice, and the memory answer. An answer asked again isn't listed. Each tool the installer installed is moved to the pinned version if it's at another, and its missing PATH entries are put back. Every tool's checklist row says what this run did: `(installed)`, `(updated from <version>)`, `(reinstalled)` when the old version couldn't be read, `(already up to date)`, or `(already installed at <folder>, left as it is)`. Skill sources whose default branch hasn't moved since the last run aren't downloaded again (see Skills above). A re-run never moves an existing top workspace.

Three overrides let it run with no network and no prompts:

- `--home <folder>` uses that folder as the user's profile folder, with local AppData inside it, and `<folder>\Program Files` standing in for the machine's Program Files. Nothing outside it is touched: changes to the user PATH and environment, the programs it would run (such as Git's installer, or T3's `t3.cmd project add` that puts the top workspace in T3's list), and the pages it would open in the browser are recorded under `<folder>\fake-machine\` instead, each program with the PATH it was given. The machine-wide PATH it searches for tools already installed is `<folder>\fake-machine\machine-path.json` (a list of folders), and the user PATH is the fake environment's. The fake machine never really waits: it has no patience for what happens after a program returns (T3 opening, My Drive appearing), unless a test gives it some in `<folder>\fake-machine\waiting.json`, and then it only counts the time, so a test can also say what appears after a while. What it only reads from the profile folder, such as T3 Code's project list (`.t3\userdata\statev2.sqlite`, opened read-only), is read from the override.
- `--answers <file>` answers every question from a JSON file. Nothing is asked and nothing waits for Enter. Pages still open, and programs still run, through the machine: without `--home` that is the real one. Its keys are the settings file's: `team` (one of the profile's team names, or `Another team`, the default, which sets up what the profile does; asked first, and only under a profile that lists teams. Jumpstart and the setup page don't read it yet), `topWorkspace` (one of the folders of the projects T3 Code already lists that look like a top workspace, that is titled as the profile's top workspace or holding one of its workspaces; or `new`, to make one where the profile says; or any folder's whole path. A folder, listed or not, is used as it is wherever it is and whatever it's called, with no Google Drive check, and one that isn't there is made if the folder it goes in is; otherwise the answer is wrong. The default is the first such project, or `new` if there's none), `googleDriveFolder` (Google Drive profiles) or `workspacesLocation` (others; either asked only for `new`; for a folder, and for Documents, `workspacesLocation` is the folder it's in and `googleDriveFolder` is null), `softwareCenter` (`install`, the default, which opens Software Center at Google Drive and waits in counted time as above, or `documents`; asked only for `new` under a profile that names Drive's entry in Software Center, when Google Drive for desktop isn't installed and Software Center offers it), `withoutGoogleDrive` (`documents`, the default, or `install-first`, which ends the run; asked only for `new` under a Google Drive profile when Google Drive for desktop isn't installed and Software Center doesn't offer it, or didn't install it within 15 minutes) and `googleDriveReady` (`again`, the default, which with answers from a file stops the run, or `documents`; asked only for `new` under a Google Drive profile when Google Drive for desktop is installed but never opened or not signed in; none of these three is saved in the settings file), `claudeSignIn` (asked after each Claude Code sign-in that didn't sign in: `again` for Try again, or `skip` for Skip for now; a list such as `["again", "skip"]` answers each failure in turn. With answers from a file the default, and what's taken once a list runs out, is `skip`, so a run with nobody at the screen never tries for ever; not saved in the settings file), `channel` (`stable` or `nightly`; not asked when T3 Code is already installed, whose channel is recorded instead), `github` (true or false), `workspaces`, `connectors` and `extraTools` (lists of names, or of ids for extra tools, from the profile), `fullSkills` (`no`, the default, `finished` or `beta`), `change` (a re-run's list of the answers to ask again, from `team`, `workspaces`, `connectors`, `extraTools`, `github`, `fullSkills` and `switchOffMemory`, as offered; default none; never saved), and `switchOffMemory` (true or false, default false; asked only of someone who has been using Claude's automatic memory, that is whose Claude settings switch it on, whose `CLAUDE_CODE_DISABLE_AUTO_MEMORY` is set to anything but `1`, or who has files in a project's `memory` folder, and when No neither switch is touched). The settings file also records `autoMemory` (`"off"` or `"left on"`) for Jumpstart. A key left out takes its default, as pressing Enter would. On a re-run the settings file's answers come first, and the answers file stands in for the person only for what the settings file doesn't know.
- `--downloads <folder>` takes downloads from that folder instead of the internet. It stands in for the internet only: each file is copied into the installer's own downloads folder as a real download would be, and that folder is never changed. A `manifest.json` there replaces the pinned one, so a test's stand-in files can pass the checksum check. That replacement is for tests only: it's reachable only through `--downloads`, which nothing but a test passes, and a real run always reads the pinned `manifest.json`. T3's release feed (`latest.yml` or `nightly.yml`) and GitHub's release list (`releases`) are read from there too.

A fourth is for tests only, and the bootstrap never passes it:

- `--profiles <folder>` takes profiles from that folder instead of `profiles/`, so a test can run a fixture profile, such as one whose team adds a connector or an extra tool. An extra tool is the manifest entries whose `when` is its id, so a fixture's new extra tool installs nothing unless the manifest has entries for it.

## Testing

```
npm test
npm run typecheck
```

The tests run the real installer end to end in a temporary home with the first three overrides, and the fourth where a test needs fixture profiles, and check only what it leaves behind: the printed checklist, the exit code, the log, the settings file, the folders, and the fake machine's PATH and record of programs run. `pasted-lines.test.js` reads the four PowerShell files as text (it never runs them) and checks the rules above, that the three bootstrap lines differ only in their top line, that their Node.js pin matches `manifest.json`, that they unpack Node.js into the installer's own folder, and that each download shows its own line with its size and a percentage instead of curl's progress bar, with `Invoke-WebRequest` kept as the fallback. `page.test.js` renders the setup page for each profile and checks it shows that profile's own line once, the three steps in order, the share-log line, each reference section in that profile's wording, every skill under its heading with its link, the T3 Code section's points and labelled screenshots, the anchors the Jumpstart skill links to, and "project" only once.
