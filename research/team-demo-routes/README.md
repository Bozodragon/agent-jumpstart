# Research: routes for the York team demo

Gathered on 12 November 2026 while grilling [Spec the small release before Monday's York session](https://github.com/Bozodragon/agent-jumpstart/issues/59). Two researchers each answered one question, and a skeptic then tried to refute each researcher's decision-relevant claims against primary sources. All four were Opus 5.5 at high effort. Where a skeptic corrected a claim, the correction sits next to it.

**Read this first.** Every Google route below needs a Google Cloud project with an OAuth client. The research couldn't tell whether York staff can create one, and it treated that as a blocker for Monday. Staff can. A colleague has already set Google Analytics up this way, with the same kind of Cloud console clicks clasp needs and no extra permissions. Read the "not by Monday" judgements below with that in mind.

Follow-ups on the map: [How Marketing gets Google Analytics](https://github.com/Bozodragon/agent-jumpstart/issues/71) and [How the Azure and Dataverse CLIs are offered, and to which teams](https://github.com/Bozodragon/agent-jumpstart/issues/72).

This branch is never merged.

## Google Analytics for the Marketing team

To read GA4 data, a York marketing person needs at least the Viewer role on the GA4 property. They also need a Google sign-in that grants the analytics.readonly scope through an OAuth client, and the client has to come from a Google Cloud project with the Analytics Data API turned on. Google has no first-party Google Analytics connector in Claude's directory. The only directory routes are the Anthropic-verified third-party connectors Supermetrics and Windsor.ai, and on York's Enterprise plan a claude.ai admin has to add a connector before anyone can connect it. Connectors added that way do reach Claude Code and T3 Code once the person is signed in with their claude.ai account.

Google runs an unannounced remote MCP endpoint at https://analyticsdata.googleapis.com/mcp/v1. I probed it today: it answered the MCP handshake, listed run_report, get_metadata, run_realtime_report and check_compatibility, and named accounts.google.com as its sign-in server. Google's documented route is the local Python server analytics-mcp, run with pipx or uvx, which signs in with Application Default Credentials (ADC) from gcloud. Both routes need one OAuth client, set up once in a York-owned Google Cloud project, but neither needs Windows admin rights.

Recommendation: the Installer adds the remote endpoint to Claude Code's user config as a Marketing-only MCP server entry, which the repo has no kind for yet. It passes the York Desktop-app OAuth client's ID and secret, which Google doesn't treat as confidential, then runs `claude mcp login` so the person signs in with their York Google account. That installs nothing, needs no Python and no admin, and can't be blocked by Constrained Language Mode. It needs someone at York to create the Google Cloud project and OAuth client, and one end-to-end test before Monday, because the endpoint is unannounced. The final design keeps it, and later moves it to a claude.ai custom connector added by York's Claude admin so it also reaches claude.ai. As a fallback for Monday that needs no setup, a skill can read a report the person exports to Google Sheets through the Google Sheets connector York already offers.

### Routes

#### Exported report plus a skill (fallback for Monday)

- **Kind, in this repo's terms.** skill (uses the existing Google Sheets/Drive connectors in profiles/york.json)
- **What the person does.** In GA4, opens a report, then Share this report > Download File > Export to Google Sheets (or CSV into the workspace). Asks the agent about it.
- **What the Installer would do.** Install a small York skill (e.g. 'ga4-reports') that tells the agent how to find and read the exported Sheet/CSV and the GA4 metric/dimension names. For Marketing, tick Google Sheets by default in the connectors walkthrough.
- **Needs admin rights on the laptop.** no. A skill is a file in the workspace, and the Sheets connector is already in York's list.
- **Needs an organisation admin or cloud setup.** None beyond Viewer on the GA4 property and the Google Sheets connector being enabled in York's claude.ai org (it is already in the profile).
- **Blockers and risks.** Not live data, and the person does a manual export step each time. Exports stop at 100,000 rows. It works in both claude.ai and Claude Code because it goes through the Sheets connector.

#### Google's remote Analytics Data MCP endpoint, added to Claude Code's user config (recommended)

- **Kind, in this repo's terms.** other: a new 'MCP server' entry kind in the profile (Claude Code user-scope MCP server), Marketing team only
- **What the person does.** Signs in once in the browser with their York Google account and approves the analytics.readonly consent, from a sign-in the Installer starts (like clasp's).
- **What the Installer would do.** Run `claude mcp add --transport http --scope user --client-id <York Desktop client>.apps.googleusercontent.com --client-secret --callback-port <port> google-analytics https://analyticsdata.googleapis.com/mcp/v1`, with MCP_CLIENT_SECRET set so there's no prompt (or write the same entry into ~/.claude.json). Then run `claude mcp login google-analytics` on screen and check that it connected. Downloads nothing, and no manifest entry is needed.
- **Needs admin rights on the laptop.** no. The entry lives in the user's ~/.claude.json and the sign-in uses a loopback browser redirect.
- **Needs an organisation admin or cloud setup.** One-off at York: a Google Cloud project in York's org with the Google Analytics Data API enabled, an OAuth consent screen (Internal, so no verification and no test-user list), and a Desktop-app OAuth client. York's Workspace API Controls must not block that client. GA4 Viewer on the property for each person. No Claude admin needed.
- **Blockers and risks.** The endpoint is unannounced: Google's MCP reference page returns 404 and the endpoint isn't on Google's supported-products list, so it could change. It has only 4 read tools (no account listing), so the person must know their property ID. Nobody has publicly confirmed a full sign-in and tool call from Claude Code yet, so test it end to end before Monday. It reaches Claude Code and T3 Code only, not claude.ai. It's unknown whether the project also needs an 'MCP enable' step, as BigQuery's server does.

#### Third-party directory connector: Windsor.ai or Supermetrics

- **Kind, in this repo's terms.** connector (a new 'connectors' entry in profiles/york.json for the Marketing team)
- **What the person does.** In claude.ai Customize > Connectors, clicks Connect, signs in to Windsor or Supermetrics, then authorises GA4 with their York Google account.
- **What the Installer would do.** Add a connectors entry (e.g. name 'Windsor.ai', what: 'read your Google Analytics reports'), which the existing walkthrough in installer/src/connectors.js already handles. Nothing is installed.
- **Needs admin rights on the laptop.** no on Windows. It does need a claude.ai org admin.
- **Needs an organisation admin or cloud setup.** A York Claude Enterprise Owner, or a custom role with 'Manage access to Libraries', must add the connector to the org first. Neither appears in the claude.ai connectors this session's account lists. York's Workspace admin may need to allow the vendor's Google OAuth app. No Google Cloud project is needed.
- **Blockers and risks.** GA data goes through a third-party processor, so York may need a DPIA or procurement review. Supermetrics is a 14-day trial, then paid. Windsor's free plan covers one data source, paid from $19/month. This is the only route that reaches claude.ai and Claude Code with no Cloud project, but it depends on York's admin and procurement before Monday.

#### Google's analytics-mcp server run locally (pipx/uvx) with ADC

- **Kind, in this repo's terms.** extra tool (uv pinned in manifest.json, plus the Google Cloud CLI for ADC) plus an MCP server entry in Claude Code's user config
- **What the person does.** Signs in to the browser login that `gcloud auth application-default login --client-id-file=<York client json> --scopes=https://www.googleapis.com/auth/analytics.readonly,https://www.googleapis.com/auth/cloud-platform` opens.
- **What the Installer would do.** Pin uv (uv-x86_64/aarch64-pc-windows-msvc.zip plus its .sha256 from GitHub releases, 'zip' install kind) and the Google Cloud CLI (google-cloud-cli-windows-x86_64-bundled-python.zip, about 105 MB, which exists at dl.google.com) as extra tools. Run the ADC login like clasp's signIn. Then `claude mcp add analytics-mcp --scope user -e GOOGLE_APPLICATION_CREDENTIALS=<path> -e GOOGLE_CLOUD_PROJECT=<York project> -- uvx analytics-mcp==1.1.0`. uv fetches its own Python for the user.
- **Needs admin rights on the laptop.** no. uv and gcloud zips unpack per-user, and uvx's managed Python is per-user.
- **Needs an organisation admin or cloud setup.** The same York Google Cloud project and OAuth client as the remote route, plus the Analytics Admin API enabled. Each user needs permission to use that project as the quota project (serviceusage.services.use). GA4 Viewer on the property.
- **Blockers and risks.** It's Google's documented and supported route, with more tools (account summaries, funnels, realtime). But it installs about 150 MB and runs a Python process. It previously hung on Windows with gcloud ADC (issues #153, #156, fixed in v0.6.0). WDAC/AppLocker could block executables in the user profile, the same risk the existing tools have. It reaches Claude Code only, not claude.ai.

#### Google's remote endpoint as a claude.ai custom connector (end state)

- **Kind, in this repo's terms.** connector (custom, added org-wide by York's Claude admin, then listed in the profile for Marketing)
- **What the person does.** Clicks Connect on 'Google Analytics' on the claude.ai connectors page and signs in with their York Google account.
- **What the Installer would do.** A connectors entry in profiles/york.json, and remove any user-scope MCP entry it added earlier, because Claude Code hides a connector when a user entry points at the same URL.
- **Needs admin rights on the laptop.** no on Windows.
- **Needs an organisation admin or cloud setup.** A York Claude Owner adds a custom connector with URL https://analyticsdata.googleapis.com/mcp/v1 and 'Use your own OAuth client'. It needs a Web-application OAuth client in York's Google Cloud project with claude.ai's callback URL, because Google doesn't support dynamic client registration.
- **Blockers and risks.** It depends on York's Claude admin and on the unannounced endpoint. It's the cleanest end state: Google first-party, no third-party processor, and it reaches claude.ai, Claude Code and T3 Code. It's unlikely to be ready by Monday.

### What the skeptic found the researcher missed

- Cheapest working Monday route not considered: a user-scope Claude Code MCP entry for Windsor.ai or Supermetrics. Both servers support dynamic client registration, so the Installer could run `claude mcp add --transport http --scope user <name> <url>` and `claude mcp login <name>` with no claude.ai admin, no Google Cloud project and no secret. The person signs in to the vendor and then authorises GA4 with their York Google account. The blockers are the third-party processor/DPIA question, York's Workspace API Controls allowing the vendor's Google OAuth app, and trial or plan limits. It reaches Claude Code and T3 Code only. Windsor also ships an official-marketplace Claude Code plugin ('windsor-ai').
- Funnel and OpenSEO are additional Anthropic-verified directory connectors that cover Google Analytics. The researcher listed only Supermetrics and Windsor.
- Secret placement: profiles/york.json is in a public GitHub repo, and GitHub secret scanning detects Google OAuth client ID+secret pairs with push protection and partner reporting to Google. The York Desktop-app client secret must not be committed to the profile. It has to come from somewhere else (e.g. served by the York install script host) and be passed via MCP_CLIENT_SECRET at `claude mcp add` time.
- Scope pinning: use `claude mcp add-json` with "oauth":{"clientId":...,"callbackPort":...,"scopes":"https://www.googleapis.com/auth/analytics.readonly"}. The endpoint's protected-resource metadata advertises the broader 'analytics' (edit) scope too, and its 401 challenge names no scope.
- Google withdrew rather than never published the remote endpoint docs: indexed developers.google.com pages 'MCP Reference: analyticsdata.googleapis.com' and 'MCP Tools Reference .../mcp/tools_list/check_compatibility' now 404. That makes relying on the endpoint for the 'final design' riskier than 'unannounced' suggests.
- Google Cloud's Manage MCP servers page says Google remote MCP endpoints are 'available as soon as you enable the service API'. roles/mcp.toolUser is required only for Google Cloud MCP servers, so enabling the Analytics Data API in York's project is probably enough, with no separate MCP-enable step or IAM grant per user.
- Google's GA agent skills include Node.js references, and the Installer already installs Node. A skill-plus-API route could avoid Python, but it still needs gcloud for ADC (or a custom OAuth flow) and a Cloud project.
- The gcloud manifest pin must use the versioned file name (google-cloud-cli-<ver>-windows-x86_64.zip), not the moving 'bundled-python' alias, and no .sha256 sidecar was found for it.
- For the export-plus-skill fallback: the person's account in this environment already lists the Google Sheets and Google Drive claude.ai connectors (Sheets is in profiles/york.json with default false). The Drive connector can likely read an exported Sheet too, so Marketing may not even need Sheets ticked.

## The Azure CLI and the Dataverse CLI for Systems, Data and Operations

Yes for the Azure CLI, and it is the cheap one to add now. Microsoft publishes a portable x64 ZIP (still marked preview) that it describes as "useful when you don't have administrative privilege". Each GitHub release publishes SHA-256 hashes for its files. The ZIP fits the manifest's existing `how: "zip"` with `check: "bin/az.cmd"` and `path: ["bin"]`. On a York laptop, `az --version` exits 0, so the Installer's run check passes, and `az login` / `az account show` fit the `signIn` shape. No Installer code change is needed: it is one extra tool plus a manifest entry.

"Dataverse CLI" is most likely Microsoft's own tool of that name: the npm package `@microsoft/dataverse` (preview, MIT licence). It has `dataverse auth create`, `data query` and a built-in MCP server. It ships per-platform native `dataverse.exe` files inside the npm package, so it fits `how: "npm"` like clasp, but it is not cheap. Two reasons:
- `dataverse --version` exits 1 ("Unknown command"), so the Installer's `--version` check would report "Windows wouldn't run it" until the code learns another way to read a version.
- Its sign-in needs York's environment URL, plus a tenant admin consent for its Entra app.

A York laptop already has a working Dataverse CLI user profile against York's crm4 environment, which suggests the consent exists.

The older Power Platform CLI (`pac`) could also be installed per user by unzipping its NuGet package (a .NET Framework build: `tools/pac.exe`). Whether `pac --version` exits 0 is unchecked, and it is not needed for the Dataverse demo. None of the three is a connector or a skill as the repo uses those words. All are extra tools. The Dataverse CLI's MCP server would be a new kind of entry (a local MCP server in Claude Code's config), and the repo has none of those yet.

### Routes

#### Azure CLI as an extra tool (portable ZIP)

- **Kind, in this repo's terms.** extra tool
- **What the person does.** Ticks the extra tool, or gets it by default from the Systems, Data and Operations team. When `az login` runs in their window, they pick their York account in the Windows sign-in dialog (WAM). If they have several Azure subscriptions, they press Enter at the subscription prompt.
- **What the Installer would do.** Download https://github.com/Azure/azure-cli/releases/download/azure-cli-2.92.0/azure-cli-2.92.0-x64.zip (sha256 2cbd2c10e4b2ec4de2ab98eaa69f51fa4c9dfc4922b5116ada88091663d92af2, 92 MB). Unpack it with tar into %LOCALAPPDATA%\Programs\<folder> (13,309 files, 285 MB unpacked, several top-level folders, so the existing `unpack` keeps it as is) and put `bin` on the user PATH. Prove it runs with `az.cmd --version` (exits 0). Sign-in: `run: ["login", "--allow-no-subscriptions"]`; `check: ["account", "show", "--query", "user.name", "--output", "tsv"]`; `signedInAs` along the lines of `^(\S+@\S+)\s*$` (the regex is untested). If az.cmd is already on the PATH, for example from a per-machine MSI, the existing logic leaves that copy in place and uses it.
- **Needs admin rights on the laptop.** no: the ZIP needs no admin. The MSI and winget routes install per-machine and do.
- **Needs an organisation admin or cloud setup.** None to install. To sign in, York's Entra tenant must not block the Azure CLI app (04b07795-8ddb-461a-bbee-02f9e1bf7b46) with Conditional Access. Doing anything useful needs Azure RBAC roles or Dataverse access that IT grants.
- **Blockers and risks.** Microsoft still calls the ZIP 'preview'. It is x64 only (ARM64 would need emulation or no entry). Big download and unpack. It runs its own python.exe and .pyd files from %LOCALAPPDATA%, so AppLocker or WDAC rules could block it, the same risk class as node.exe; the existing `--version` check would catch that. Without `--allow-no-subscriptions`, staff with no Azure subscription can't sign in usefully. Device-code fallback is often blocked by Conditional Access, which Microsoft recommends. WAM is the default on Windows since 2.61. `az upgrade` does not apply to a ZIP copy; the Installer replaces the folder, which matches Microsoft's advice for the ZIP.

#### Dataverse CLI (@microsoft/dataverse) as an extra tool via npm

- **Kind, in this repo's terms.** extra tool (its `mcp` command would also make it a local MCP server, a category the repo doesn't have yet)
- **What the person does.** Ticks it. When `dataverse auth create --environment <York env URL>` runs, they sign in with their York account in a browser or the system dialog.
- **What the Installer would do.** Download https://registry.npmjs.org/@microsoft/dataverse/-/dataverse-1.0.88.tgz (sha256 75d32c12be32e20d531b15e17f6f62bfca12ec777e4f018403c574d28157e632, computed here; 145 MB, 181 MB unpacked because it carries binaries for six platforms). Install it with the existing `how: "npm"` path into its own folder, not clasp's `npm` folder: `check: "dataverse.cmd"`, `path: ["."]`. The .cmd shim runs bin/dataverse.js, which starts bin/win-x64/dataverse.exe or win-arm64/dataverse.exe. Sign-in: `run: ["auth", "create", "--environment", "https://<org>.crm4.dynamics.com"]`; `check: ["auth", "who"]`; `signedInAs` along the lines of `^\s*User:\s+(\S+)`. `auth who` exits 0 and prints a 'User:' line. Needs a code change first: `putInPlace` and `versionThere` run `--version`, which this CLI rejects with exit 1. It would need, for example, a per-tool version-arguments field, or reading the version from node_modules/@microsoft/dataverse/package.json.
- **Needs admin rights on the laptop.** no: an npm global install into a per-user prefix needs no admin.
- **Needs an organisation admin or cloud setup.** Yes. A tenant admin must consent once for the Dataverse CLI app 0c412cc3-0dd6-449b-987f-05b053db9457 (Microsoft's README says this is needed before users can authenticate). For its MCP server, a Dataverse admin must also turn on Dataverse MCP for the environment and allow that client. Each user needs a security role in the environment.
- **Blockers and risks.** Preview; 8+ releases since March 2026, so expect churn. The `--version` check means an Installer code change. The York environment URL would be hard-coded in manifest.json's signIn.run, because sign-in is per tool, not per profile. Large download. The native .exe runs from %LOCALAPPDATA%, so AppLocker could block it. MCP use would mean writing Claude Code MCP config, which the Installer doesn't do today.

#### Power Platform CLI (pac) as an extra tool from the NuGet package

- **Kind, in this repo's terms.** extra tool
- **What the person does.** Ticks it. When `pac auth create` runs, they sign in with their York account in the Entra dialog.
- **What the Installer would do.** Download https://api.nuget.org/v3-flatcontainer/microsoft.powerapps.cli/2.14.1/microsoft.powerapps.cli.2.14.1.nupkg (61 MB, 191 MB unpacked). Pin a sha256 computed by the repo, as for the clasp tgz; NuGet itself publishes SHA-512. Unpack with `how: "zip"` (tar reads a .nupkg as a zip): `check: "tools/pac.exe"`, `path: ["tools"]`. It is the .NET Framework build that needs .NET Framework 4.6.2, which is built into Windows 11, and it includes `pac data`, which the .NET-tool build lacks. The same file serves x64 and arm64: it carries win-x64, win-arm64 and win-x86 msalruntime files. Sign-in: `run: ["auth", "create"]` (no `--environment` means the default environment); `check` would be `auth who` or `auth list`, whose output format here is unverified.
- **Needs admin rights on the laptop.** no for the unpacked NuGet package and for the .NET tool route (per user, but it needs the .NET SDK). The MSI is probably per user too (log paths under %LOCALAPPDATA%\Microsoft\PowerAppsCLI suggest so), but it is a bootstrapper that pulls the same NuGet package and isn't documented either way.
- **Needs an organisation admin or cloud setup.** None known for interactive user sign-in. A Dataverse security role is needed to do anything.
- **Blockers and risks.** Unverified whether `pac --version` exits 0. Documented: `pac` with no arguments prints the version on its second line. If it doesn't exit 0, the same code change as for the Dataverse CLI is needed. The nuspec sets requireLicenseAcceptance=true, and unpacking skips the licence prompt that the MSI shows. Overlaps the Dataverse CLI, and is not the 'Dataverse CLI' Microsoft now ships.

#### Dataverse MCP remote endpoint as a claude.ai custom connector

- **Kind, in this repo's terms.** connector
- **What the person does.** Connects it on claude.ai's Connectors page, like the York connectors.
- **What the Installer would do.** Nothing beyond listing it in the profile's `connectors` and sending the person to the page.
- **Needs admin rights on the laptop.** no on the laptop.
- **Needs an organisation admin or cloud setup.** Yes, heavy. York must register a custom Entra app with the Dynamics CRM mcp.tools permission, add it to the environment's allowed MCP clients, and add a custom connector for the org in claude.ai. Whether claude.ai's connector OAuth works with that app is untested.
- **Blockers and risks.** Not achievable by Monday without York IT. Listed only so the planning session knows a connector route exists.

### What the skeptic found the researcher missed

- Dataverse MCP tool calls cost money. Microsoft's Dataverse MCP page says `search_data` is billed at the Tenant graph grounding Copilot Credit rate, and every other tool at the 'Text and generative AI tools (basic)' rate. Non-Microsoft clients such as Claude Code and Claude Desktop are named as billed. Both the Dataverse CLI `mcp` route and the claude.ai Dataverse connector would need a York billing setup. The CLI's plain `data query` commands are probably not MCP-billed (unverified). Source: https://learn.microsoft.com/power-apps/maker/data-platform/data-platform-mcp
- A Microsoft-published 'Microsoft Dataverse' connector is in Anthropic's directory (claude.com/marketplace/connectors/dataverse). In the repo's terms this is a connector entry in profiles/york.json, not an extra tool. It needs a Power Platform admin to enable the Claude client for the environment and a claude.ai owner to allow it.
- The Azure CLI may already be a route to Dataverse that needs no consent for the Dataverse CLI app. Microsoft's Dataverse Web API PowerShell quick start uses Az's first-party token (Get-AzAccessToken -ResourceUrl <org URL>). The Azure CLI equivalent, `az account get-access-token --resource https://<org>.crm4.dynamics.com` (or `az rest`), is my inference and untested. If it works under York's Conditional Access, the Systems, Data and Operations team could reach Dataverse with only the cheap Azure CLI extra tool on Monday. Source: https://learn.microsoft.com/power-apps/developer/data-platform/webapi/quick-start-ps
- The pac MSI is a per-user, no-elevation install, not just 'probably per user'. Its Directory table targets LocalAppDataFolder\Microsoft\PowerAppsCLI, it has no ALLUSERS, and Word Count = 10. But it is an unversioned bootstrapper (powerapps-cli-1.0.msi) that downloads pac from NuGet. The repo's `installer` path runs the file directly, which won't work for a .msi without msiexec, and its checksum wouldn't pin pac's version. The NuGet .nupkg remains the better fit.
- ARM64: the Azure CLI ZIP is x64 only, and tools.js picks tool.downloads[process.arch], so on an ARM64 laptop it is 'not installed' unless the manifest maps arm64 to the x64 ZIP. Windows 11 on ARM emulates x64, but that is untested here. The Dataverse CLI and the pac nupkg both carry arm64 binaries.
- The Dataverse CLI's `dataverse install latest` self-updates with `npm install -g`, outside the Installer's per-tool prefix, and would put a second copy on npm's default prefix. The Installer would then see a newer copy than its pin and 'replace' it on the next run.
- Dataverse CLI profiles share PAC CLI's store (%LOCALAPPDATA%\Microsoft\PowerAppsCLI\authprofiles_v2.json). A person who signs in with pac or the Dataverse CLI is seen as signed in by the other's `auth who`. That affects the Installer's 'already signed in, skip' logic if both tools are offered.
- For the Azure CLI sign-in check: when not signed in, `az account show` exits non-zero, so the existing whoIsSignedIn logic works. Once signed in, `az account show --query user.name -o tsv` prints just the UPN, so a simple ^(\S+@\S+)\s*$ with the 'm' flag should match (still untested here).

- Whether `pac --version` (or bare `pac`) exits 0 on Windows.
