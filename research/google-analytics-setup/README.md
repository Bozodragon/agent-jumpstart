# Research: how the Installer takes over the Google Analytics and Search Console setup

Gathered on 13 November 2026 for [How Marketing gets Google Analytics](https://github.com/Bozodragon/agent-jumpstart/issues/71). It builds on [the team demo research](https://github.com/Bozodragon/agent-jumpstart/tree/research/team-demo-routes/research/team-demo-routes) and doesn't repeat it. The sources are Google's docs, the source code of analytics-mcp, mcp-server-gsc, google-auth (Python and Node), uv, T3 Code and the Claude Agent SDK, and live probes of Google's endpoints made today. Nothing here was tested with a York Google account.

This branch is never merged.

## The colleague's setup, for reference

He created a Google Cloud project, enabled the Google Analytics Admin API, the Google Analytics Data API and the Google Search Console API, and set up an OAuth consent screen (Internal) and a Desktop-app OAuth client. Two Python login scripts (google-auth-oauthlib `InstalledAppFlow.run_local_server`) wrote two `authorized_user` credentials files. One has analytics.readonly + cloud-platform and a `quota_project_id`. The other has webmasters.readonly. Claude Code's `~/.claude.json` then runs `uvx --python 3.12 analytics-mcp` (env `GOOGLE_APPLICATION_CREDENTIALS`, `GOOGLE_CLOUD_PROJECT`) and `npx -y mcp-server-gsc@0.3.0` (env `GOOGLE_APPLICATION_CREDENTIALS`).

## What this means for the design

- **The Cloud console clicks can't be scripted, so one shared York project is the cheap route.** Google has no supported API, gcloud command or Terraform resource that creates a consent screen or a Desktop-app OAuth client (Q1). Someone at York does those clicks once. Each person then needs only a York Google account and access to the GA4 properties and Search Console sites, with no IAM role on the project, as long as the credentials file has no `quota_project_id` (Q2).
- **The Installer can do the sign-in itself, in Node, with no Python login scripts.** One loopback OAuth sign-in asking for analytics.readonly + webmasters.readonly gives one `authorized_user` file that both servers accept (Q4, Q5). Leave out cloud-platform: analytics-mcp doesn't need it, and it pulls the token under Google Cloud session control. Leave out `quota_project_id`, so no one needs `serviceusage.services.use`. Leave out `GOOGLE_CLOUD_PROJECT`, which analytics-mcp never reads.
- **The client secret is the snag.** Google says a Desktop client's secret "is obviously not treated as a secret", but its OAuth policy also says "You must never commit client credentials into publicly available code repositories". GitHub push protection blocks Google OAuth client secrets and reports them to Google (Q3). Keep the secret out of the repo.
- **Google now runs undocumented remote MCP endpoints for Search Console and the Analytics Admin API**, as well as the Analytics Data one already known (Q5). None is announced, so they aren't a base for the design yet. If they become documented, they'd remove uv, Python, npx and the credentials file: one `claude mcp add` each, signed in through Claude Code's own OAuth.

## 1. Can the consent screen, the OAuth client and API enabling be scripted?

**Consent screen and Desktop client: no, not through anything Google supports (confirmed).** **API enabling: yes (confirmed).** **Deep links: a multi-API enable link is confirmed; the Google Auth Platform links are confirmed as URLs, but the `?project=` form only from a third-party tool.**

- The only API that ever created consent screens ("brands") and OAuth clients was the IAP OAuth Admin API (`gcloud iap oauth-brands create`, `gcloud iap oauth-clients create`, Terraform `google_iap_brand` / `google_iap_client`). It made IAP clients, not Desktop-app clients. It was deprecated on 22 January 2025, closed to new projects on 19 January 2026 and shut down on 19 March 2026. Google's migration guide says existing clients are now "managed through the Google Cloud console". [IAP deprecations](https://docs.cloud.google.com/iap/docs/deprecations), [Migrate from the IAP OAuth Admin API](https://docs.cloud.google.com/iap/docs/deprecations/migrate-oauth-client)
- `gcloud iam oauth-clients` is a different thing: OAuth clients for Workforce Identity Federation, not Google sign-in clients. [Manage OAuth application](https://docs.cloud.google.com/iam/docs/workforce-manage-oauth-app)
- The only automation found is unofficial. AnswerDotAI's gclientid drives a signed-in Chrome over the DevTools protocol to click through the console. Its README says "Google provides no supported API for a general-purpose OAuth client". It creates the project and enables APIs through the Resource Manager and Service Usage REST APIs. It can make an Internal consent screen (`--internal`) and a Desktop client (`--desktop`). [gclientid](https://github.com/AnswerDotAI/gclientid). Not something to ship to marketing staff.
- API enabling is scriptable: `gcloud services enable analyticsadmin.googleapis.com analyticsdata.googleapis.com searchconsole.googleapis.com --project=X`, or the Service Usage `services:batchEnable` REST call (up to 20 services per call). [Enable and disable services](https://docs.cloud.google.com/service-usage/docs/enable-disable). Either one needs a token with the cloud-platform scope and `serviceusage.services.enable` on the project, which means installing gcloud and signing in first. For a one-off, a deep link is cheaper.
- An ordinary York user can create a project: when an organization resource is created, "all users in your domain are automatically granted Project Creator ... and Billing Account Creator" (York could have removed this, but the colleague's project shows it hasn't). [Creating and managing organization resources](https://docs.cloud.google.com/resource-manager/docs/creating-managing-organization). New-project link: `https://console.cloud.google.com/projectcreate` (from [Create a Google Cloud project](https://developers.google.com/workspace/guides/create-project)).
- Multi-API enable link. Google's own Apigee docs use a single link with comma-separated APIs: `https://console.cloud.google.com/apis/enableflow?apiid=apigee.googleapis.com,apigeeconnect.googleapis.com,...&redirect=https%3A//console.cloud.google.com` ([Apigee hybrid: Enable APIs](https://docs.cloud.google.com/apigee/docs/hybrid/latest/precog-enableapi)). So for this case: `https://console.cloud.google.com/apis/enableflow?apiid=analyticsadmin.googleapis.com,analyticsdata.googleapis.com,searchconsole.googleapis.com&project=PROJECT_ID`. The `flows/enableapi?apiid=` form is widely used too. Adding `&project=` is the console's normal parameter, but I didn't load this exact link signed in.
- Google Auth Platform pages. Google's docs link `console.developers.google.com/auth/overview`, `/auth/branding`, `/auth/audience`, `/auth/scopes` and `/auth/clients` ([Configure the OAuth consent screen](https://developers.google.com/workspace/guides/configure-oauth-consent), [Manage OAuth Clients](https://support.google.com/cloud/answer/15549257)). gclientid's code opens these with a project (from [gclientid/oauth.py](https://github.com/AnswerDotAI/gclientid/blob/main/gclientid/oauth.py)):
  - `https://console.cloud.google.com/auth/overview?project=PROJECT_ID` (Get started, when the project has no consent screen yet)
  - `https://console.cloud.google.com/auth/branding?project=PROJECT_ID`
  - `https://console.cloud.google.com/auth/audience?project=PROJECT_ID` (Internal / External)
  - `https://console.cloud.google.com/auth/scopes?project=PROJECT_ID`
  - `https://console.cloud.google.com/auth/clients/create?project=PROJECT_ID` (choose Desktop app)
- Client secrets are now hashed: the console shows a secret in full only once, at creation, and after that only its last four characters. A client can hold two secrets at a time for rotation. [Manage OAuth Clients](https://support.google.com/cloud/answer/15549257). Whoever creates the shared client must download the JSON straight away.
- Clients unused in token exchanges for six months are deleted automatically, with an email 30 days before. [Manage OAuth Clients](https://support.google.com/cloud/answer/15549257), [OAuth 2.0 Policies](https://developers.google.com/identity/protocols/oauth2/policies)

## 2. Shared project or one per person: what does each person need?

**With a shared York project and an Internal consent screen, each person needs nothing on the project itself (confirmed from source and Google's docs, not tested at York).**

- **`GOOGLE_CLOUD_PROJECT` does nothing for analytics-mcp (confirmed from source).** analytics-mcp calls `google.auth.default(scopes=...)` and throws the project ID away (`self._credentials, _ = ...`, [client.py](https://github.com/googleanalytics/google-analytics-mcp/blob/main/analytics_mcp/tools/client.py)). google-auth uses `GOOGLE_CLOUD_PROJECT` only for the project ID it returns. The quota project comes from the file's `quota_project_id` or the `GOOGLE_CLOUD_QUOTA_PROJECT` variable ([_default.py](https://github.com/googleapis/google-auth-library-python/blob/main/google/auth/_default.py), [environment_vars.py](https://github.com/googleapis/google-auth-library-python/blob/main/google/auth/environment_vars.py)). Neither analytics-mcp, google-analytics-data 0.23.3, google-analytics-admin 0.30.2 nor google-api-core 2.44.0 contains the string `GOOGLE_CLOUD_PROJECT` (searched the PyPI wheels). Google's [setup page](https://developers.google.com/analytics/devguides/MCP) and the repo README recommend setting it, and the troubleshooting text says it fixes a missing quota project. The code doesn't back that up.
- **If the file has a `quota_project_id`, every person needs `serviceusage.services.use` on that project (confirmed).** The library then sends `x-goog-user-project`, and "You must have the `serviceusage.services.use` IAM permission for a project to be able to designate it as your billing project" ([Troubleshoot ADC](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc), [System parameters](https://docs.cloud.google.com/apis/docs/system-parameters)). The permission comes with Owner, Editor or Service Usage Consumer. The colleague created the project, so they presumably hold Owner on it, which would explain why his file works. A colleague using his file's settings would need that role granted.
- **With no quota project, calls count against the project that owns the OAuth client (confirmed in substance).** The Data API quotas page: "All API calls made using credentials or an API key from your project will count against" its quotas ([Data API quotas](https://developers.google.com/analytics/devguides/reporting/data/v1/quotas)). gcloud's own reference: "If --client-id-file is specified, the quota project will not be written to ADC" ([gcloud auth application-default login](https://docs.cloud.google.com/sdk/gcloud/reference/auth/application-default/login)). google-auth only warns about a missing quota project when the client is gcloud's own (`CLOUD_SDK_CLIENT_ID`), because that client belongs to Google's shared project ([_default.py](https://github.com/googleapis/google-auth-library-python/blob/main/google/auth/_default.py)). So the three APIs must be enabled in the client's project and nowhere else.
- **mcp-server-gsc** never reads a project ID. It hands the file to google-auth-library's `GoogleAuth({ keyFile })` ([search-console.ts](https://github.com/ahonn/mcp-server-gsc/blob/main/src/search-console.ts)). The Node library's `UserRefreshClient` honours `quota_project_id` if the file has one ([refreshclient.ts](https://github.com/googleapis/google-auth-library-nodejs/blob/v9.15.1/src/auth/refreshclient.ts)), so the same rules apply.
- **Who can sign in.** An Internal consent screen is for the Workspace organization that owns the project, with no test-user list and no Google verification ([Configure the OAuth consent screen](https://developers.google.com/workspace/guides/configure-oauth-consent)). Each person also needs at least Viewer on the GA4 property and access to the Search Console site.
- **The cost of sharing: the quota is shared too.** A standard GA4 property allows 14,000 tokens per project per property per hour, against 40,000 per property per hour across all projects ([Data API quotas](https://developers.google.com/analytics/devguides/reporting/data/v1/quotas)). Every York user of the shared client draws on the same 14,000 for the same property. Search Console allows 1,200 queries per minute per user and per site, and 40,000 per minute per project ([Search Console API limits](https://developers.google.com/webmaster-tools/limits)), which won't bind.

## 3. Can a Desktop-app client ID and secret go in a public GitHub repo?

**No: Google's policy forbids it and GitHub blocks it (confirmed). What Google does when it's reported is unknown.**

- Google says Desktop apps "are public clients and cannot keep secrets confidential" ([OAuth 2.0 for iOS & Desktop Apps](https://developers.google.com/identity/protocols/oauth2/native-app)), and that for installed apps "the client secret is obviously not treated as a secret" ([Using OAuth 2.0](https://developers.google.com/identity/protocols/oauth2)). The same native-app page lists `client_secret` as optional in the token exchange and refresh requests (untested; google-auth's Python loader still requires the key to be present in an `authorized_user` file, [credentials.py](https://github.com/googleapis/google-auth-library-python/blob/main/google/oauth2/credentials.py)).
- Google's OAuth policy still says: "You must never commit client credentials into publicly available code repositories", and "We highly recommend that you avoid committing them to any code repository." [OAuth 2.0 Policies](https://developers.google.com/identity/protocols/oauth2/policies)
- GitHub secret scanning has a pattern for Google OAuth client ID + secret pairs (`google_oauth_client_id`, `google_oauth_client_secret`), with partner alerts to Google, user alerts and push protection ([Supported secret scanning patterns](https://docs.github.com/en/code-security/reference/secret-security/supported-secret-scanning-patterns)). A push to this repo would be blocked, and a bypass would be reported to Google.
- I found no Google statement that it disables or revokes a leaked OAuth client secret. The automatic disabling Google documents is for service account keys. For OAuth clients Google tells the developer to rotate the secret ("change immediately in the case of a leak"). [Manage OAuth Clients](https://support.google.com/cloud/answer/15549257). Unknown whether a partner report leads Google to act on the client.
- Ways around it: serve the client JSON from somewhere York controls, inject it into the Installer at build time from a GitHub Actions secret (the built Installer still carries it, which Google's model expects for Desktop apps), or have the person paste or pick the JSON during setup.

## 4. Does analytics-mcp need cloud-platform, the Admin API, or anything else?

**analytics.readonly alone works with an `authorized_user` file (confirmed by a Google maintainer and the source). The Admin API is still needed for half the tools (confirmed). Latest version is 1.1.0 (confirmed).**

- Latest release v1.1.0 on 6 November 2026 (v1.0.0 on 3 November, v0.8.0 on 22 October). PyPI: `requires_python >=3.10`, depends on google-analytics-data 0.23.3, google-analytics-admin 0.30.2, google-auth ~=2.62, mcp >=2.3.0,<3, google-adk >=2.11.0. [Releases](https://github.com/googleanalytics/google-analytics-mcp/releases), [PyPI](https://pypi.org/project/analytics-mcp/)
- The only scope in the code is analytics.readonly (plus analytics.edit with `--allow-write`) ([client.py](https://github.com/googleanalytics/google-analytics-mcp/blob/main/analytics_mcp/tools/client.py)). For user credentials even that request is ignored: google-auth's `Credentials.requires_scopes` returns False because "OAuth 2.0 credentials have their scopes set when the initial token is requested and can not be changed" ([credentials.py](https://github.com/googleapis/google-auth-library-python/blob/main/google/oauth2/credentials.py)).
- Google's GA team said so in [issue #187](https://github.com/googleanalytics/google-analytics-mcp/issues/187) (closed 15 July 2026): "The `cloud-platform` scope is required by the `gcloud auth application-default login` command", the override "is *ignored* by user credentials", and a refresh token "limited to the read-only Google Analytics scope ... would work as well", in an `authorized_user` file with `client_id`, `client_secret`, `refresh_token` and `universe_domain`.
- Dropping cloud-platform has a second benefit. Google Cloud session control (a Workspace admin setting) makes apps that use the cloud-platform scope re-authenticate when the session length runs out ([Workspace Updates, Nov 2020](https://workspaceupdates.googleblog.com/2020/11/session-length-cloud-console-update-exempt-apps.html), [Session controls for reauthentication](https://docs.cloud.google.com/access-context-manager/docs/session-controls-for-reauthentication)). Whether York sets it is unknown.
- Admin API tools: `get_account_summaries`, `get_property_details`, `list_google_ads_links`, `list_property_annotations`, `list_key_events` (plus the write tools). Data API tools: `run_report`, `run_funnel_report`, `run_conversions_report`, `run_realtime_report`, `get_custom_dimensions_and_metrics`. Without the Admin API, the person can't list their properties and must know the property ID. [tools/admin](https://github.com/googleanalytics/google-analytics-mcp/tree/main/analytics_mcp/tools/admin)
- Windows: the hang with user credentials ([#134](https://github.com/googleanalytics/google-analytics-mcp/issues/134), [#156](https://github.com/googleanalytics/google-analytics-mcp/issues/156)) is fixed. Current code also patches `subprocess.Popen` around `google.auth.default()` to stop a Windows deadlock. #134 was first reported on Python 3.14, which may be why the colleague's setup pins 3.12. Pinning is still sensible, because grpcio wheels lag new Pythons.

## 5. One sign-in for both servers, and which Search Console server

**One `authorized_user` file with analytics.readonly + webmasters.readonly can serve both (confirmed from both servers' source; not run end to end).**

- Neither server can narrow the scopes of a user credential. In Python, `requires_scopes` is False. In Node, the refresh request carries only `refresh_token`, `client_id`, `client_secret` and `grant_type`, with no scope ([oauth2client.ts](https://github.com/googleapis/google-auth-library-nodejs/blob/v9.15.1/src/auth/oauth2client.ts)). Each server uses whatever the refresh token was granted, so one token with both scopes works for both.
- **mcp-server-gsc accepts `authorized_user` files**, although its README only describes service accounts. The published 0.3.0 does `new google.auth.GoogleAuth({ keyFile: credentials, scopes: [webmasters.readonly] })` (read from the npm tarball's `dist/search-console.js`), and google-auth-library's `fromJSON` builds a `UserRefreshClient` for `type: "authorized_user"` ([googleauth.ts](https://github.com/googleapis/google-auth-library-nodejs/blob/v9.15.1/src/auth/googleauth.ts)). The colleague's setup is the proof in practice.
- **Who maintains it.** ahonn (Yuexun Jiang), one person. 285 stars. npm releases 0.1.0 to 0.2.0 in December 2024, 0.2.1 in December 2025, 0.3.0 on 13 February 2026. The repo has unreleased commits up to 4 September 2026 (JSON-string credentials, a Cloudflare Worker remote mode). [npm](https://www.npmjs.com/package/mcp-server-gsc), [repo](https://github.com/ahonn/mcp-server-gsc). Its dependencies are caret ranges, so `npx -y mcp-server-gsc@0.3.0` can resolve different dependency versions on each machine.
- **Better maintained: AminForou/mcp-gsc** (PyPI `mcp-search-console`, 0.4.2 released 6 November 2026, 2,196 stars, MIT, pushed 6 November 2026). It runs under `uvx`, like analytics-mcp. It does its own browser sign-in from `GSC_OAUTH_CLIENT_SECRETS_FILE` and keeps a `token.json` in its own config folder, or takes a service account through `GSC_CREDENTIALS_PATH`. It asks for webmasters.readonly by default. [repo](https://github.com/AminForou/mcp-gsc), [gsc_server.py](https://github.com/AminForou/mcp-gsc/blob/main/gsc_server.py). It doesn't read a standard `GOOGLE_APPLICATION_CREDENTIALS` file, so sharing one sign-in with analytics-mcp would mean writing its `token.json` (untested).
- **No Google-official local Search Console MCP server exists** (searched; third-party guides as late as 4 November 2026 say the same).
- **Google does run an undocumented remote one.** Probed today without credentials:
  - `https://searchconsole.googleapis.com/mcp` answers `initialize` (server name "StatelessServer"). `tools/list` gives `query` (searchanalytics.query), `sites_list` and `get`. Its protected-resource metadata names accounts.google.com, with scopes webmasters and webmasters.readonly. `/mcp/v1` returns 404.
  - `https://analyticsadmin.googleapis.com/mcp` answers too, with 12 read tools: `list_account_summaries`, `get_property`, `list_properties`, `list_accounts`, `get_account`, `list_google_ads_links`, `list_reporting_data_annotations`, `list_data_streams`, `list_custom_dimensions`, `list_custom_metrics`, `list_key_events`, `get_data_retention_settings`. A tool call without a token gets `401` with `WWW-Authenticate: Bearer realm="https://accounts.google.com/"`.
  - `https://analyticsdata.googleapis.com/mcp/v1` is unchanged since the earlier research: 4 tools, scopes analytics.readonly and analytics.
- **Is the remote Analytics endpoint announced? No (confirmed as of 13 November 2026).** Google's list of supported remote MCP servers has about 90 entries and none for Analytics or Search Console ([Supported products](https://docs.cloud.google.com/mcp/supported-products)). The [Analytics MCP page](https://developers.google.com/analytics/devguides/MCP) describes only the local server. Candidate doc paths for Search Console and Analytics MCP pages return 404.

## 6. Can gcloud's default client get analytics.readonly or webmasters.readonly?

**No (confirmed for non-Cloud scopes in general; not tried with these two scopes).** Google's ADC troubleshooting page says "Access blocked" errors come from "scopes that aren't supported by the default ADC setup command", typically non-Google Cloud scopes, and that the fix is your own OAuth client (`--client-id-file`) or service account impersonation. [Troubleshoot ADC](https://docs.cloud.google.com/docs/authentication/troubleshoot-adc). analytics.readonly and webmasters.readonly are not Cloud scopes. Every route therefore needs an OAuth client in some Cloud project (or a service account, which needs a project too and has to be added to each GA4 property and Search Console site).

## 7. Does T3 Code load user-scope MCP servers from `~/.claude.json`?

**Yes, by default (confirmed from source and docs; not tested with a user-scope server on a T3 thread).**

- T3 Code's Claude adapter builds the `query()` options without `settingSources` ([ClaudeAdapterV2.ts](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts), commit 4aec277 of 13 November 2026). It only sets `settingSources` for its own settings lookups, and `strictMcpConfig` only for a capability probe in `ClaudeProvider.ts`. It pins `@anthropic-ai/claude-agent-sdk` ^0.3.321.
- The SDK (0.3.321 `sdk.d.ts`): "When omitted, all sources are loaded (matches CLI defaults)." Anthropic's docs: omitting it "is equivalent to `["user", "project", "local"]`", and the "`~/.claude.json` global config" is "Always read", relocated only by `CLAUDE_CONFIG_DIR`. [Use Claude Code features in the SDK](https://code.claude.com/docs/en/agent-sdk/claude-code-features)
- One catch: T3 Code can run Claude with a custom home (its `homePath` setting or a different `CLAUDE_CONFIG_DIR`). Then "user scope" means that folder's `.claude.json`, not `%USERPROFILE%\.claude.json`. The Installer should add servers with `claude mcp add --scope user` under the same environment rather than edit a fixed path.
- For remote OAuth servers: "The SDK doesn't open a browser or run an interactive OAuth flow". A server needs a sign-in done earlier in interactive Claude Code on the same machine, or it reports `needs-auth`. [Agent SDK MCP](https://code.claude.com/docs/en/agent-sdk/mcp). Local stdio servers with a credentials file aren't affected.

## 8. uv on Windows: per-user Python 3.12 with no admin

**Confirmed: a non-elevated Windows 11 process installed and ran CPython 3.12.13 through uv. Blocking is possible if York's proxy blocks releases.astral.sh and GitHub.**

- uv 0.13.8 (12 November 2026) ships `uv-x86_64-pc-windows-msvc.zip`, `uv-aarch64-pc-windows-msvc.zip` and `uv-i686-pc-windows-msvc.zip`, each with a `.sha256`. [Releases](https://github.com/astral-sh/uv/releases)
- Test today on the York laptop (uv 0.11.13, process not elevated): `uv python install 3.12` downloaded `https://releases.astral.sh/github/python-build-standalone/releases/download/20260510/cpython-3.12.13%2B20260510-x86_64-pc-windows-msvc-install_only_stripped.tar.gz` (20.9 MiB) and installed it in 5 s. The default install folder is `%APPDATA%\uv\python` (`uv python dir`). `uvx --python 3.12` downloads automatically when no 3.12 is found: "By default, uv will automatically download Python versions when needed". [Python versions](https://docs.astral.sh/uv/concepts/python-versions/)
- Where it downloads from: `releases.astral.sh` by default, which mirrors python-build-standalone's GitHub releases. The docs imply a fallback to GitHub: they say that when `UV_ASTRAL_MIRROR_URL` is set, uv uses "only the configured mirror URL and does not fall back to GitHub or raw GitHub" (added in 0.11.14). `UV_PYTHON_INSTALL_MIRROR` points CPython downloads elsewhere, and `UV_PYTHON_DOWNLOADS_JSON_URL` replaces the built-in list. [Environment variables](https://docs.astral.sh/uv/reference/environment/). Packages come from pypi.org and files.pythonhosted.org. A proxy that blocks releases.astral.sh and github.com would stop it. The Installer could also ship a pinned python-build-standalone archive itself and point uv at it.
- uv registers each managed Python in `HKCU\Software\Python\Astral` (PEP 514), per user, no admin ([windows_registry.rs](https://github.com/astral-sh/uv/blob/0.11.13/crates/uv-python/src/windows_registry.rs)). Watch out: `uv python uninstall` deletes every Astral registry entry that isn't in the current install folder. When I uninstalled a test install with a different `UV_PYTHON_INSTALL_DIR`, it removed the entry for the laptop's existing Python 3.14 as well (I put it back by hand). The Installer should never set `UV_PYTHON_INSTALL_DIR` to something other than what the person's uv uses.
- python.exe runs from `%APPDATA%`. The AppLocker/WDAC risk noted in the earlier research still applies.

- Whether Google accepts a Desktop client's token exchange and refresh without `client_secret` (its native-app page lists it as optional).
- What Google does when GitHub reports a leaked OAuth client secret.
- Whether York's Workspace sets Google Cloud session control or API Controls that would affect a York-owned Internal client.
- Whether the `?project=` deep links and the multi-API `apis/enableflow` link work as expected for a York account. They weren't loaded signed in.
- Whether the undocumented `searchconsole.googleapis.com/mcp` and `analyticsadmin.googleapis.com/mcp` endpoints complete a sign-in and tool call from Claude Code with a York Desktop client. Untested, and they could change or disappear.
- Whether 14,000 tokens per project per property per hour is enough when the whole Marketing team shares one client against the same property.
