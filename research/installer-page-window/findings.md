# Facts for How the Installer page works

Gathered while grilling [How the Installer page works](https://github.com/Bozodragon/agent-jumpstart/issues/69). Three Opus researchers at high effort, each checked by an Opus skeptic at high effort. Local tests ran on one unmanaged Windows 11 PC (build 26300), not on a York laptop. Each claim is marked confirmed (with its evidence) or unconfirmed. The skeptic's corrections follow each report and take precedence.

## Electron, an app window or a tab

Short version: a chrome-less window from the browser already on the laptop (b) gives almost all of what Electron (a) would give, for very little cost. Electron costs a lot and adds a new risk. A normal tab (c) costs nothing but looks like a website.

(a) Electron 45.3.2, the current stable release, is a 151 MB download that unpacks to 357 MB. The Node zip the bootstrap downloads today is 40 MB. Electron's own electron.exe is NOT digitally signed. Renaming it or changing its icon doesn't make that worse, but it stays unsigned unless we pay for an EV signing certificate. On a laptop whose rules allow only signed or approved programs, an unsigned 250 MB exe in the user's folder is the kind of file that gets blocked. Node.exe is signed by the OpenJS Foundation. Electron does contain Node 24, which is new enough for the Installer. But two places in the Installer assume node.exe sits next to npm. Inside Electron they would break, so we would either keep downloading Node as well or change that code.

(b) Edge with --app opened a plain window on this PC: a title bar with the page's name, no address bar, no tabs. When the page called window.close(), the window closed and every Edge process exited. Edge is always at the same place on Windows 11 and is found without admin. A fresh profile (--user-data-dir) signed itself into the Windows account and showed a "syncing your data" pop-up in a normal tab. In the app window no pop-up showed. Nothing extra to download.

(c) A normal tab works today, and window.close() closed it too.

In all three, Claude, GitHub and clasp sign-ins open in the person's default browser (Chrome at York). So with (a) or (b) the person moves between two windows, and with (c) between two tabs. The Installer's window never needs the York Google account. Closing the PowerShell window is a separate fix in the bootstrap, and it is the same for all three options. React works in all three.

### Findings

- **confirmed.** The current stable Electron is v45.3.2, published 2026-11-13. Its Windows x64 zip is 158,318,730 bytes (about 151 MiB).
  - Evidence: gh api repos/electron/electron/releases/latest -> 'v45.3.2 2026-11-13T00:47:03Z electron-v45.3.2-win32-x64.zip 158318730'
- **confirmed.** The downloaded zip matched Electron's published SHA256 (cd1ab0d4...a98b).
  - Evidence: sha256sum electron.zip == SHASUMS256.txt line for electron-v45.3.2-win32-x64.zip (https://github.com/electron/electron/releases/download/v45.3.2/SHASUMS256.txt)
- **confirmed.** Unpacked, Electron is 374,358,378 bytes (about 357 MiB) in 73 files. electron.exe alone is 250,056,704 bytes.
  - Evidence: Expand-Archive then Get-ChildItem -Recurse | Measure-Object Length -Sum -> files=73 bytes=374358378; (Get-Item electron.exe).Length -> 250056704
- **confirmed.** For comparison, the Node zip the bootstrap downloads today (node-v26.12.1-win-x64.zip) is 41,901,456 bytes (about 40 MiB).
  - Evidence: bootstrap/install.ps1:28 nodeVersion='26.12.1'; curl -I https://nodejs.org/dist/v26.12.1/node-v26.12.1-win-x64.zip -> Content-Length: 41901456
- **confirmed.** The prebuilt electron.exe from Electron's GitHub release has no Authenticode signature. Its DLLs are unsigned too, except Microsoft's own d3dcompiler_47.dll.
  - Evidence: Get-AuthenticodeSignature electron.exe -> Status NotSigned; dxcompiler.dll, electron_wer.dll, ffmpeg.dll, vk_swiftshader.dll, vulkan-1.dll NotSigned; d3dcompiler_47.dll Valid CN=Microsoft Windows

Removing the unsigned warnings takes a paid certificate (Electron's docs say EV certificates since June 2023) or Azure Artifact Signing, which only some countries can use.
  - Evidence: Unsigned status above; https://www.electronjs.org/docs/latest/tutorial/code-signing ('Windows will treat your app as completely unsigned'; EV required since June 2023; Azure Artifact Signing 'gets rid of SmartScreen warnings', limited countries)
- **confirmed.** Node.exe, by contrast, is signed by the OpenJS Foundation. Checked on this PC's Node 24 install. The pinned Node 26.12.1 in %LOCALAPPDATA% was not checked.
  - Evidence: Get-AuthenticodeSignature 'C:\Program Files\nodejs\node.exe' -> Valid CN=OpenJS Foundation
- **confirmed.** Unsigned electron.exe ran without admin from a folder under %LOCALAPPDATA% (the Temp scratch folder) on this unmanaged PC. Not tested on a York laptop.
  - Evidence: ELECTRON_RUN_AS_NODE=1 electron.exe -e ... ran and printed versions; path was under C:\Users\jacob\AppData\Local\Temp\...; Get-AppLockerPolicy -Effective on this PC -> 0 rule collections
- **confirmed.** Neither curl.exe nor Invoke-WebRequest -UseBasicParsing in Windows PowerShell 5.1 writes Mark-of-the-Web (a Zone.Identifier stream). So SmartScreen's downloaded-file prompt does not fire on what the bootstrap downloads.
  - Evidence: powershell.exe 5.1.26100.9818: Invoke-WebRequest -UseBasicParsing -OutFile iwr.txt and System32\curl.exe -o curl.txt; Get-Item -Stream * and dir /r show only :$DATA on both. Background: https://textslashplain.com/2016/04/04/downloads-and-the-mark-of-the-web/
- **confirmed.** AppLocker's default executable rules allow everyone to run programs only from %windir% and %programfiles% (admins can run anything). A policy built from those defaults blocks any exe in AppData, signed or not.
  - Evidence: https://learn.microsoft.com/en-us/windows/security/application-security/application-control/app-control-for-business/applocker/executable-rules-in-applocker (default rules table)
- **unconfirmed.** York has no AppData-blocking default path rules, because node.exe already runs from %LOCALAPPDATA% there. Whether York has publisher or WDAC rules that treat signed and unsigned exes differently, which would let node.exe through and block electron.exe, is unknown.
  - Evidence: Inferred from the York laptop check quoted in the task. No York AppLocker/WDAC policy was seen.
- **confirmed.** Electron 45.3.2 bundles Node 24.22.2 and Chromium 156. That satisfies the Installer's engines >=22.20.0 and supports ESM.
  - Evidence: ELECTRON_RUN_AS_NODE=1 electron.exe -e -> {"node":"24.22.2","electron":"45.3.2","chrome":"156.0.8078.100"}; installer/package.json:4-6
- **confirmed.** Inside Electron, process.execPath points to electron.exe, and the Electron folder has no npm.cmd. Two parts of the Installer assume node.exe: tools.js:172 runs npm.cmd from beside process.execPath, and tools.js:278 runs a package's bin script with process.execPath. Without the pinned Node install, or without ELECTRON_RUN_AS_NODE=1 for those child processes plus a separately shipped npm, both would break.
  - Evidence: execPath output above; ls of unpacked Electron (no npm/npx); installer/src/tools.js:172 and :278
- **confirmed.** ELECTRON_RUN_AS_NODE makes electron.exe behave as plain Node. It is ignored if the runAsNode fuse is disabled, which hardened Electron apps commonly do.
  - Evidence: https://www.electronjs.org/docs/latest/api/environment-variables
- **confirmed.** msedge.exe --app=<url> opens a window with a title bar showing the page title, minimise/maximise/close buttons, and no address bar or tabs.
  - Evidence: Ran Edge 157.0.4341.46 with --app=http://127.0.0.1:56305/ --user-data-dir=<scratch> --no-first-run --window-size=900,640; screenshot showed window titled 'Agent Jumpstart test' with page content only
- **confirmed.** In that app window, window.close() closed the window and every Edge process for that profile exited.
  - Evidence: Server log showed /log?closing=1 and never /log?still-open-after-close=1; Get-CimInstance msedge.exe filtered by profile path -> 0 processes
- **confirmed.** A normal Edge tab opened from the command line (history length 1) also closed on window.close().
  - Evidence: Same test without --app: server logged closing=1, 0 processes left. MDN: browser-opened windows 'may only be closed if they have not been navigated (history length remains 1)' https://developer.mozilla.org/en-US/docs/Web/API/Window/close
- **confirmed.** A fresh Edge profile (--user-data-dir) signed itself into the Windows account and showed a 'We are now syncing your browsing data' dialog in a normal tab. In the --app window no dialog appeared during the 6-second test. Edge's ImplicitSignInEnabled policy (on by default) governs this.
  - Evidence: Screenshot of the tab test; https://learn.microsoft.com/en-us/deployEdge/microsoft-edge-browser-policies/implicitsigninenabled
- **confirmed.** Edge is registered at a fixed path that can be found without admin: HKLM App Paths\msedge.exe = C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe, signed by Microsoft Corporation.
  - Evidence: Get-ItemProperty 'HKLM:\SOFTWARE\Microsoft\Windows\CurrentVersion\App Paths\msedge.exe' on this PC; Get-AuthenticodeSignature -> Valid CN=Microsoft Corporation
- **unconfirmed.** Edge is present at that path on every Windows 11 machine, York's included.
  - Evidence: Checked only on this PC. Not checked on a York laptop.
- **unconfirmed.** Chrome registers App Paths\chrome.exe under HKLM for a system install and under HKCU for a per-user install (%LOCALAPPDATA%\Google\Chrome\Application). Both can be read without admin. On this PC Chrome is not installed (default browser is Opera), so the Chrome --app test was not run.
  - Evidence: https://www.chromium.org/developers/installer/ ; this PC: HKCU/HKLM App Paths\chrome.exe absent, UserChoice ProgId = OperaStable
- **unconfirmed.** Running chrome.exe --app=<url> without --user-data-dir while Chrome is already open hands the window to the running Chrome and exits at once. The window then uses the person's signed-in York profile, and the Installer cannot track it by process.
  - Evidence: Known Chromium single-instance behaviour; not tested here
- **confirmed.** In every option, sign-ins are opened with rundll32 url.dll,FileProtocolHandler, so they go to the person's default browser regardless of how the Installer's own page is shown.
  - Evidence: installer/src/machine.js:531

### Risks

- Electron: York AppLocker or WDAC rules that allow only signed or approved programs could block the unsigned electron.exe even though signed node.exe runs. Nobody has tested electron.exe on a York laptop.
- Electron: about 151 MB extra to download, on top of or instead of the 40 MB Node zip, and 357 MB on disk. That is slow on poor Wi-Fi, and antivirus may scan a 250 MB unsigned exe at length or quarantine it.
- Electron: signing it means buying an EV certificate or using Azure Artifact Signing (limited to some countries). Electron also needs regular security updates.
- Electron: the Installer's npm.cmd lookup (tools.js:172) and its bin-script launcher (tools.js:278) assume process.execPath is node.exe. Inside Electron's main process they would break unless the pinned Node is kept or the code changes.
- App window: Edge with a fresh profile can sign itself into the Windows (York Microsoft) account and show sync or first-run pop-ups in normal tabs. --no-first-run did not stop the sync dialog in a normal tab. A managed Edge may also be under York policies (e.g. BrowserSignin, startup pages) that change what appears.
- App window: without --user-data-dir, Chrome or Edge hands the window to a browser already running, so the Installer cannot tell when the window closes from the process. Only page-level signals (the page stops talking to the local server) will work.
- App window: on a York laptop, Chrome may be installed only per user (App Paths in HKCU), or York may have uninstalled or blocked Edge. The lookup needs a fallback to a normal tab.
- All options: sign-ins open in the default browser (Chrome), so in (a) and (b) the Installer window can end up behind Chrome, and people need a clear 'come back to this window' cue. In (c) the sign-in is just another tab.
- All options: the PowerShell window the person pasted into stays open until it is closed. iex cannot run exit, so hiding or closing the terminal is a separate bootstrap change (e.g. launching node detached), and no choice of window fixes it.

### Skeptic: corrections

- **Claim:** Closing the PowerShell window is a separate bootstrap change that is the same for all three options. iex cannot run exit, so no choice of window fixes it.
  - **Why:** It is a bootstrap change, but the report makes it sound harder and more uniform than it is. (1) It already works in Constrained Language Mode. I started powershell.exe 5.1, switched it to ConstrainedLanguage, and ran this through iex: Start-Process node.exe -WindowStyle Hidden, then Stop-Process -Id $PID. The log showed the mode was 'ConstrainedLanguage' and that a .NET call was blocked ('net-blocked'). The PowerShell process exited, and node was still running 5 seconds later: it wrote 'alive pid 55872 ppid 46492', and 46492 was the PowerShell that had been killed. (2) The options do differ. electron.exe is a windowed (GUI-subsystem) program: its PE header has subsystem 2, while node.exe has 3, which is console. A windowed program never shares the PowerShell console, so closing that window cannot kill it. node.exe is a console program, so it has to be started detached, as above. Today the bootstrap runs it attached (bootstrap/install.ps1:202 '& $nodeExe @arguments'), which is why the terminal stays open now.
  - **Correction:** Confirmed on this PC with simulated Constrained Language Mode, not a real AppLocker-enforced one, and not on a York laptop. With any of the three options, the bootstrap can start the Installer hidden or detached with Start-Process and then close its own window with Stop-Process -Id $PID. Neither cmdlet needs exit or .NET. Electron gets this almost for free because it never takes over the console. Plain node needs -WindowStyle Hidden.
- **Claim:** Removing the unsigned warnings takes a paid EV certificate (Electron's docs say EV is required since June 2023) or Azure Artifact Signing, which only some countries can use.
  - **Why:** The docs quote is accurate. But it describes SmartScreen warnings, and the report itself found that the bootstrap's downloads carry no Mark-of-the-Web, so SmartScreen's prompt never fires on them. The real gate is AppLocker, App Control/WDAC, Smart App Control or antivirus. Those check for any valid Authenticode signature or publisher, not for EV. The pinned Node 26.12.1 is a good example. I downloaded node-v26.12.1-win-x64.zip and checked node.exe with Get-AuthenticodeSignature: 'Valid CN=OpenJS Foundation, issuer=CN=Microsoft ID Verified CS EOC CA 04'. That issuer is Microsoft's Artifact Signing (formerly Trusted Signing) service, not an EV certificate. So the binary that already runs on York laptops is signed the non-EV way.
  - **Correction:** EV is not the only route. The signing method that Node itself uses (Microsoft ID Verified / Artifact Signing) would give electron.exe a valid signature. Whether a Canadian organization or individual is eligible is unconfirmed: the Microsoft Learn quickstart lists Azure regions (none in Canada), not which publishers' countries qualify. For this download path, signing matters for York's app-control rules and antivirus, not for SmartScreen.
- **Claim:** Node.exe is signed by the OpenJS Foundation (checked only on this PC's Node 24; the pinned Node 26.12.1 was not checked).
  - **Why:** This isn't wrong, just incomplete. I checked the pinned version.
  - **Correction:** Confirmed: node.exe extracted from https://nodejs.org/dist/v26.12.1/node-v26.12.1-win-x64.zip has a valid signature from CN=OpenJS Foundation, issued by Microsoft ID Verified CS EOC CA 04.

### Skeptic: missed

- Size comparison mixes packed and unpacked figures. The report sets Electron's 357 MB on disk against Node's 40 MB zip. The fair comparison is 151 MB vs 40 MB to download, and 357 MB (73 files) vs about 118 MB (2,398 files) on disk. The Node figure comes from 'unzip -l node-v26.12.1-win-x64.zip' -> 118132572 bytes, 2398 files, and node.exe alone is 105,319,752 bytes. Electron is still about 3.8x bigger to download and about 3x bigger on disk. Confirmed.
- Smart App Control is not mentioned at all. On Windows 11 it blocks unsigned or low-reputation programs whether or not the file carries Mark-of-the-Web, so it could block an unsigned electron.exe while allowing the signed node.exe. On this PC it is off: HKLM\SYSTEM\CurrentControlSet\Control\CI\Policy VerifiedAndReputablePolicyState = 0. Its state on York laptops is unconfirmed. Managed devices usually have it off, but that is not verified.
- Electron's support window: the Electron team supports only the latest three stable major versions, and a new major ships every 8 weeks (https://www.electronjs.org/docs/latest/tutorial/electron-timelines). So a pinned Electron loses security fixes in roughly 6 months, and the 151 MB download would have to be re-pinned and re-downloaded on that schedule. Electron 45.3.2 also ships Chromium 156, while Edge on this PC is already 157.0.4341.46. Confirmed from the docs and from the electron.exe version output.
- The WebView2 runtime is already on this PC (HKLM\SOFTWARE\WOW6432Node\Microsoft\EdgeUpdate\Clients\{F3017226-...} pv = 157.0.4341.46) and is signed and updated by Microsoft. It is another way to get a chrome-less window without shipping 151 MB, but it needs a native host program, which would again be ours and unsigned. Confirmed present on this PC; not checked on a York laptop.
- If the terminal closes, the failure path moves. Today, when the run fails, the bootstrap prints the 'irm .../share-log.ps1 | iex' help line in the terminal (bootstrap/install.ps1:203-207). With a hidden or closed terminal, that message has to be shown on the Installer page instead, in every option. Confirmed by reading the file.
- Pop-up console windows from child programs: the Installer runs npm.cmd, installers and similar console programs. In a cheap test, electron.exe (ELECTRON_RUN_AS_NODE=1, started with no console) and a hidden node.exe each started powershell.exe children with and without windowsHide. Children of the Electron parent reported no console window (GetConsoleWindow = 0) either way. Children of the hidden node had a console window that was not visible (hwnd=590324 visible=False) without windowsHide, and none with it. So no flashing window was detected in either setup. Caveats: this tested run-as-node mode, not a real Electron main process, and nobody watched the screen. Whether windows visibly flash on a York laptop is unconfirmed.
- The npm/execPath problem is narrower than 'keep downloading Node as well'. Electron's main process could start the existing Installer with the pinned node.exe as a child process. Then tools.js:172 and :278 keep working unchanged, but the person downloads both Electron (151 MB) and Node (40 MB). That is an inference from the code, not tested.

## Taking the person out of the PowerShell window

Yes. I tested this on this Windows 11 machine with Windows PowerShell 5.1 in the restricted mode York laptops may use. The paste line can start the Installer as a hidden program, and the person can then close the PowerShell window. Closing it stopped a normal program after about 4 seconds. The hidden one kept running in both window types: the classic black window and Windows Terminal, which is what Windows 11 opens by default.

The paste line can also tell when the page has opened. The Installer writes a small "page connected" file, and the paste line checks for it. If the file appears, the window says "you can close this window now". If no page opens within 20 seconds, the window runs the Installer the way it does today. Both outcomes worked in the restricted mode. The paste line can even close the window itself with "exit". That command is banned today, so allowing it is a choice for the project to make.

Three things need building before this works for real:
1. Today, signing in to Claude, GitHub and one other tool happens by typing or pasting a code into the window. A hidden Installer has no window to type into, so these sign-ins must move into the page.
2. With no window, people can't stop the Installer by closing it. The page needs a Stop button. Otherwise the only way is Task Manager, where it shows as "Node.js JavaScript Runtime". The Installer must also shut itself down if the page is closed and not reopened. I showed it can notice the page going away within a fraction of a second.
3. Pasting the line a second time while a hidden Installer is still running would not be blocked. Two Installers could run at once, so the Installer needs a check for one already running.

Starting the Installer hidden this way also stops programs it runs in the background from flashing windows. Electron (a desktop-app framework) has no such hidden window. Under Electron, every background program would need to be started hidden, or it pops up a terminal window.

## React for the Installer page, and outside requests

The round-two prototype is not React. It is about 74 KB of plain, hand-written HTML, CSS and JavaScript in five files. It also loads its two fonts, Instrument Sans and JetBrains Mono, from Google Fonts. That line was copied from the setup page, which does the same thing. The setup page is plain HTML too, and its own test explicitly allows those fonts to come from Google.

"No outside requests" means the page asks only the laptop for anything, never the internet. In practice it rules out two things. First, the Google Fonts line: in a test with the internet blocked, the prototype still worked but quietly switched to Windows' own fonts. With the internet on, it fetched both fonts from Google, so Google learns each time someone runs it. Second, loading React from a public CDN (a library-hosting website). It does not rule out React itself. When React is packed into the page's own script file at build time ("bundled"), the page is served entirely from the laptop. I checked this: a small React 19 page rendered in Edge 157 with every internet address blocked, and the only requests were to the laptop itself. The fonts are free to ship with the page (OFL licence, about 72 KB).

What React costs this repo:
- One build tool (esbuild, 2 packages), plus React and its type definitions, all used only when building.
- A build step in bootstrap/build.js, which today only copies files and zips them.
- A one-line type-checking setting (the jsx option). No file renaming is needed.
- About 220 KB of script (69 KB compressed).
- Screen tests would need about 47 more test-only packages, or the logic kept separate and tested as today.

It should work the same in a tab, an app window and Electron later, because all three use the same browser engine. Only the tab is tested.
